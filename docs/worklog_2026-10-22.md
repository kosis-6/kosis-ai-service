## 2. 회고: 오늘 부딪힌 문제와 해결

| 문제 | 원인 | 해결 |
|---|---|---|
| "20대 혼인 신고율"을 통계와 무관한 질문으로 분류 | 질문 유형 설명이 모호 | 프롬프트에 "지원 안 하는 지표라도 통계 질문이면 other 아님" 명시 |
| 지원 안 하는 지표인데 "어느 지역이냐"고 되물음 | 코드가 지역을 지표보다 먼저 확인 | **지표 먼저** 확인하도록 순서 변경 |
| LLM이 연도별 증감을 직접 계산, 2025년 값은 "오류 같다"며 빼버림 | LLM에게 원자료만 주고 해석을 맡김 | 연도별 증감을 **코드가 미리 계산** |
| 2030년 질문에 수록 기간 안내 없이 추계값만 답함 | 프롬프트 규칙을 LLM이 빠뜨림 | 상황별 **답변 지침을 코드가 정해서** 함께 전달 |
| 계산값 -26,764명을 LLM이 계속 -27,664명으로 적음 | LLM이 숫자를 옮겨 적다 틀림 (규칙으로는 못 막음) | 답변 숫자를 계산 결과와 대조하는 **숫자 확인** 추가 → 오류 발견 |
| ↑ 근본 해결 | | **숫자는 코드만 출력**, LLM은 설명 문장만 |
| LLM이 코드 출력물을 베껴 쓰고 숫자를 넣음 | LLM에게 숫자를 보여줬기 때문 | LLM에는 **숫자를 뺀 정보**(지역·기간·증가/감소·순서)만 전달 |
| 출처를 지어냄 ("2023.05.31 기준" 등), "A%라면 B%" 같은 가정 | 같은 원인 | 출처·주의사항도 코드가 출력, 지침에서 가정 금지 |
| 연달아 질문하면 오류 (429 호출 제한) | 질문 하나에 LLM 2번 호출 | 아직 미해결 → 재시도 기능 필요 |

**배운 점**
- 프롬프트로 "하지 마"라고 하는 것보다, **LLM이 할 수 없게 구조를 만드는 것**이 확실하다.
  (숫자를 안 보여주면 숫자를 틀릴 수 없다)
- 문제를 고치기 전에 **잡아내는 장치**(숫자 확인)부터 만들면 원인이 보인다.
- 테스트는 정상 질문만이 아니라 **답할 수 없는 질문**(없는 지표, 없는 연도, 같은 이름 지역, 원인 질문)으로 해야 문제가 드러난다.

## 3. 내일 할 일: 4가지 방법으로 계산해서 비교하기

목적: 우리 서비스가 내는 숫자가 **정말 맞는지** 확인. 전처리 과정에서 값이 바뀌거나 빠지지 않았는지도 확인.

| 방법 | 어떻게 | 역할 |
|---|---|---|
| A. 원본 데이터 | 원본 CSV(`data/raw/kosis_zip/`)를 pandas로 직접 읽어 계산 | 전처리 전 값 |
| B. 전처리 데이터 | 우리 서비스 (`qa.py` → `kosis.duckdb`) | 검증 대상 |
| C. Claude | 같은 원본 숫자를 Claude에게 주고 계산시키기 | LLM 계산의 정확도 참고 |
| D. 직접 계산 | KOSIS 사이트에서 값 조회 + 엑셀/계산기로 계산 | **정답 기준** |

**진행 순서**
1. 테스트 질문 5~10개 정하기. 질문 유형(값, 추이, 비교, 순위)을 골고루 넣고, 함정이 있는 질문도 넣기
   - 행정구역이 바뀐 지역 (예: 군위군이 대구로 편입)
   - 100세 이상 인구가 포함되는 고령인구 비율
   - 시군구를 더해 시도를 만드는 경우
2. 질문마다 A~D 값을 표 하나에 모으기 (질문 / A / B / C / D / 일치 여부)
3. 값이 다르면 D(KOSIS)를 정답으로 보고 원인 찾기
   - A ≠ B → 전처리 문제
   - A = B ≠ D → 원본 수집이나 계산식 문제
   - C만 다름 → LLM 계산 오류 (오늘처럼 숫자를 코드가 맡는 이유의 근거)
4. 결과를 정리해서 기록. 필요하면 `validate.py` 검증 항목에 추가

**그 밖에**
- CLOVA 429 오류 재시도 기능 (`clova.py` 수정, 허락 후 진행)
- LLM 설명 문장의 군더더기("KOSIS를 참고하세요", "언제든 연락주세요") 다듬기

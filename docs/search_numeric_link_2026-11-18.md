# 통계표 찾기 ↔ 수치 계산 잇기 (2026-11-17 ~ 18)

작성: 최세진 (Claude Code와 함께). 브랜치 `feature/sj`. 이 문서는 PR에서 무엇을, 왜, 어떻게 바꿨는지와 **팀원이 해야 할 일**을 정리한다.

## 0. 한 줄 요약

통계표 찾기(탐색)는 표를 잘 찾는데 수치 계산이 그 결과를 거의 쓰지 못해 표 안내로 끝나는 질문이 많았다. 탐색이 찾은 후보 표를 그대로 넘겨받아 **여러 표를 동시에 계산해 보고**, 칸을 못 고르면 **LLM이 칸을 고르고**, 모두 안 되면 **값까지 계산한 대안을 제안**하도록 이었다. 같이 지표 사전 · 답 문장 · 적재의 결함 몇 가지를 고쳤다.

## 1. 팀원이 해야 할 일 ⚠

### 1-1. 단위가 합쳐진 표 4개를 다시 적재 (필수)

KOSIS가 일부 표에서 항목마다 다른 단위를 한 글자로 합쳐 준다 (예: 출생아 수와 합계출산율 행 모두 단위가 `명 가임여자 1명당 명`). 그래서 DB의 단위가 틀려 있고, 표에서 바로 계산할 때 "출생아 수 640,089 가임여자 1명당 명" 같은 답이 나올 수 있었다. 이번 PR은 **적재 단계에서 단위를 나누도록** 고쳤다 (`backend/config/unit_fixes.toml`, `pipeline/load_raw.py`). 이미 적재된 DB는 다시 적재해야 바뀐다.

| 표 | 내용 |
| --- | --- |
| `DT_1B8000G` | 월 · 분기 · 연간 인구동향 (칸마다 출생아수 · 조출생률 · 혼인건수 …) |
| `DT_1B81A23` | 출생아 수 · 합계출산율 |
| `DT_1B81A21` | 합계출산율 · 연령별 출산율 |
| `DT_1B81A17` | 합계출산율 · 연령별 출산율 |

방법 (원본 CSV를 `backend/data/processed/`에 두고, 컨테이너 또는 가상환경에서):

```bash
cd backend
python -c "
from pathlib import Path
from pipeline.load_worker import _load
for t in ['DT_1B8000G', 'DT_1B81A23', 'DT_1B81A21', 'DT_1B81A17']:
    _load(Path('data/processed') / f'{t}.csv', t)
"
```

- `_load`는 적재 뒤 단계(지역 매핑 · 인구 집계)까지 처음 적재와 같게 돈다. 예전 행은 이력(`raw.stat_value_history`)으로 간다.
- 확인 결과(11/18): 네 표 모두 행 수 · 값 합계 **그대로**, 단위만 바뀜. 지표 사전 답(출생아 수, 합계출산율) 그대로. 못 나눈 행 0.
- 원본 CSV는 공유 드라이브 `data_700`에 있다. `python pipeline/load_raw.py <표ID>`로 적재해도 단위는 나뉘지만 적재 뒤 단계는 돌지 않는다.
- 일반혼인율 · 일반이혼율(남편 · 아내)의 단위는 데이터에 없어 KOSIS 지표 정의로 "15세 이상 남자(여자) 인구 1천 명당 건"이라 적었다. **확인 필요**.

## 2. 왜 바꿨나

- `/ask`는 지표 사전이 먼저 답하고, 사전이 모르는 지표일 때만 통계표 찾기로 넘어간다. 넘어가도 탐색이 만든 후보 · 조건 확인(✔/✘) · 검토 판단을 수치 계산이 거의 쓰지 않고, **표 하나**로만 계산해 보다 안 되면 표 안내로 끝났다.
- 계산은 "칸 이름이 질문에 글자 그대로 있어야" 칸을 골랐다. 맞는 표를 찾아 놓고도 "결혼" ↔ "혼인"처럼 낱말이 다르면 계산하지 못했다 (탐색 시뮬레이션: 정답 표가 후보에 든 483문항 중 299문항이 칸 고르기에서 막힘).
- 예전 방식은 후보 표를 차례로 보다 "처음 계산되는 표"를 썼다. 계산이 된다고 맞는 표는 아니어서, 정답 표를 골라 놓고 2 · 3순위의 **다른 통계로 숫자를 낸** 경우가 있었다.
- 지표 사전 쪽에도 개발셋에서 틀리는 원인이 있었다: "등록된 외국인 비율"을 다른 개념인 외국인주민 비율로 답함, 추이 답에 연평균 증감률이 없음, 반올림한 값끼리 빼서 변화량 끝자리가 틀림 등.

## 3. 무엇을 어떻게 바꿨나

### 3-1. 넘기기 꾸러미 (탐색 → 계산)

- `table_guide.find_tables`가 응답에 `handoff`를 붙인다: 질문 이해, 지표마다 후보 최대 5개(고른 표 + 질문 전체 검색의 다른 묶음), 후보마다 조건 확인(`checks`) · 검토 판단 · 판 · 멤버 · 수록 기간 · 주석. 화면에 나가는 표 안내 문장은 그대로다.
- `multi.handoff`가 지표 하나 질문에도 질문 전체 검색 상위(`whole`)를 만든다 (LLM · 임베딩 호출 없음).
- 확인: 저장된 응답으로 668문항을 다시 돌려 **고른 표 · 순위가 바뀐 문항 0**.

### 3-2. 받는 쪽: 후보를 동시에 계산 (`dynamic_indicator.compute_from_handoff`)

- 후보 목록: 고른 표 → 물은 연도를 담은 같은 묶음의 다른 판 → 나머지 후보 (최대 5개). `asyncio.gather`로 동시에 계산하고, **성공한 것 중 우선순위가 높은 것**을 쓴다. KOSIS에서 받는 일은 동시에 3개까지.
- 건너뛰는 후보: 조건 ✘가 있음 / 고른 표가 아닌데 확인한 조건이 없음 / 검토가 고른 표를 '모두 충족'으로 봄.
- 탐색이 읽은 질문 이해(Gemma)를 계산용 해석으로 옮겨 쓴다. 빈 칸만 수치 해석(HCX)으로 채운다.
- 빼 달라는 대상(`exclude`), 묻는 대상(`target`) 검사를 되살렸다. 대상 낱말 검사는 검토가 '모두 충족'이거나 칸 고르기 LLM이 "담고 있다"고 답한 표에는 하지 않는다 (뜻으로 판단한 결과를 믿는다).
- 시뮬레이션(지표 하나 507문항): 정답이 아닌 표로 숫자를 낸 문항 **19 → 2**.

### 3-3. 칸 고르기 LLM (`app/services/cell_pick.py`, 프롬프트 `app/prompts/cell_pick.py`)

- 규칙(글자 맞추기)이 칸을 못 고른 표에서만 LLM 1회가 칸 번호를 고른다. 번호는 목록에 있는 것만 고를 수 있다. LLM이 "이 표에 질문의 값이 없다"고 하면 계산하지 않는다 (안전장치 유지).
- 고른 칸은 되묻기에서 사용자가 고른 칸과 같은 자리(`forced`)로 넘겨 **기존 계산 · 검증을 그대로** 탄다. 성공하면 계산 방법 캐시에 남아 다음엔 LLM 없이 계산한다.
- 질문의 낱말을 바꿔 읽었으면 답에 "질문의 '결혼'을(를) 표의 '혼인'(으)로 보고 계산했습니다"를 붙인다.
- 지역 · 연령 · 성별 분류는 코드가 고르므로 보내지 않는다. 칸 80개가 넘는 분류는 합계와 질문과 글자가 겹치는 칸만 보낸다.
- **Gemma 응답 잘림 수정**: 응답 모양(json_schema)을 강제하면, 모델이 핵심 답을 쓴 뒤 필수 칸이 남아 있을 때 공백만 이어 쓰다 글자 수 한도에 잘렸다 (시험한 세 표 모두). 칸 순서를 `fits → reason → read_as → picks`(핵심 답을 맨 뒤)로 바꿔 해결했고, 그래도 잘리면 다 쓴 칸은 살리는 `app/services/llm_json.py`를 쓴다.

### 3-4. 모두 실패하면 대안을 값과 함께 제안 (`app/services/alternative.py`)

- 코드가 대안을 만들고 값까지 계산한다 (연도만 안 맞은 표 → 그 표의 가장 가까운 해, 규칙으로 건너뛴 다른 표). LLM 1회(Gemma 기본)는 질문의 답으로 쓸 만한 것만 고른다 (대상 · 개념 · 값의 뜻 · 기간 단위가 다른 것은 버림).
- "요청하신 조건을 모두 만족하는 통계는 찾지 못했습니다. 대신 이런 자료가 있습니다. ① … ② … 어느 것으로 볼까요?" 사용자가 고르면 미리 계산한 답을 그대로 준다 (되묻기 종류 `alternative`, 화면은 기존 선택지 버튼).
- 측정(Gemma): 대안이 계산되는 28문항 중 정답이 아닌 23문항에서 19개를 걸러 내고, 정답 대안 5개 중 4개를 제안.

### 3-5. 지표 사전이 못 한 새 질문도 다른 표에서 (관문 넓히기)

- 사전이 `missing_data` · `out_of_range` · `region_not_in_year`로 끝난 새 질문도 통계표 찾기 + 꾸러미 계산을 한다 (`table_guide.SEARCH_AFTER`, `ask_session._search_after`). 계산되면 "(사전이 못 한 이유) 그래서 다른 통계표에서 찾아 계산했습니다", 안 되면 사전의 안내 그대로 + 찾은 표 카드. 추계값 제안이 이미 있는 답은 넘기지 않는다.

### 3-6. 지표 사전 · 답 문장

| 바꾼 것 | 왜 | 어디 |
| --- | --- | --- |
| 새 계산 지표 `등록외국인 비율` = 등록외국인 수 ÷ 주민등록 총인구 × 100 | "등록된 외국인 비율"이 별칭 "외국인 비율"에 걸려 행정안전부 외국인주민 비율로 답했다 | `indicators.py`, `catalog_notes.toml` |
| 외국인주민 수 · 비율에 시군구 표 출처 | 시군구 질문이 "시도 단위까지만"으로 끝났다 | `catalog_notes.toml` |
| "몇 프로"를 물으면 같은 이름의 비율 지표로 | "비율"이라는 말 없이 물으면 수로 답했다 | `qa._ratio_sibling` |
| 추이 변화량 · 증감률을 반올림 전 값으로 | 반올림한 값끼리 빼서 끝자리가 0.01 틀렸다 | `indicators.trend` |
| 모든 추이에 연평균 증감률 | 정답지가 요구하는데 계산하지 않았다 (비율 %p 추이는 제외) | `qa._add_trend_facts`, `qa._body` |
| 비율 지표 추이에 "비율 자체는 ~% 커짐" | %p와 구분해 증감률을 보여 준다 | `indicators.trend`, `qa._body` |
| 두 값을 나눈 지표의 값 답에 분자 · 분모 | 근거 숫자를 보여 준다 (등록외국인 비율 · 세대당 인구 · 인구밀도) | `indicators.value`, `qa._body` |
| 계산 지표도 사전의 주의 문구를 답에 | 조회 지표만 붙이고 계산 지표는 빠져 있었다 (중위연령 · 등록외국인 비율) | `indicators._base` |
| 세대당 인구 별칭 ("한 세대에 사는 사람", "한 세대에 평균" …) · 추이 증감률 | 질문 글자에 별칭이 없어 '근거 없는 지표'로 넘어갔다 | `catalog_notes.toml`, `indicators.py` |
| "제주"처럼 같은 시도 안의 시와 이름이 겹치면 시도로 답하고 알림 | 매번 제주특별자치도 / 제주시를 되물었다. "광주"처럼 다른 시도의 시와 겹치면 그대로 되묻는다 | `indicators.resolve_region` |

## 5. 알려진 한계 · 다음 할 일

- 지표가 여럿인 질문(두 표의 비율 · 합 · 교집합)은 아직 지표 하나처럼 계산한다 (다음 PR).
- 월 · 분기 · 반기 질문은 계산이 연 단위 자료만 읽어 숫자로 답하지 못한다. 대안 판단은 연간 값을 대신 쓰지 않도록 했다.
- 실패 뒤 원인을 보고 검색어를 고쳐 다시 찾는 단계는 없다 (에이전트 흐름 재설계에서 할 일).
- 칸 고르기로 되묻는 질문이 늘었다 (LLM이 "정할 수 없음"이라고 한 분류를 묻는다). 되묻기가 적절한지 최종 측정에서 본다.
- 표에서 바로 계산한 답의 지표 이름이 칸 이름을 이어 붙인 모양일 때가 있다 (예: "○○ 현황 총계 합계 수").

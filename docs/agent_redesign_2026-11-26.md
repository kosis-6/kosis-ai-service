# 에이전트(답 판정 고리) 수정 설계 2026-11-26

기준 코드: origin/develop `4ebe6fd`. 판정 고리 행동 이름 변경(`recell` → `repick`)만 `refactor/repick` 브랜치 `a44b84b`에 있다 (푸시 전).
설계도: 파이프라인 설계도 페이지 4절(현재) · 10절(이 문서의 안).

## 0. 요약

- 지금 판정 고리는 **값이 나온 답이 틀렸을 때만** 고친다. 기본으로 꺼져 있고(`ANSWER_JUDGE`), A1 평가에서 판정이 '다시'를 낸 71건 중 고친 것은 11건이다.
- 행동이 여섯 개(replan · requery · retable · repick · reroute · give_up)이지만 실제로 갈리는 동작은 셋(replan / `_recompute` / give_up)이다.
  - 행동이 **고칠 단계가 아니라 사정**(표 찾기를 했느냐, 처음 답이 어느 경로냐)으로 나뉘어 있다.
  - 근거("1위 확실", "칸 실패 흔적")도 흩어져 있다.
- 바꾸는 안은 세 가지다.
  1. 행동을 **고칠 단계 기준 넷**(repick 칸 · retable 표 · replan 계획 · give_up)으로 줄이고, 좁은 것부터 쓴다.
  2. 행동을 고르는 근거를 코드 **검사** 하나로 모은다. 검사는 질문 조건이 표의 칸으로 이어지는지, 값 종류와 주제가 맞는지 본다. 사전 게이트와 판정 고리가 같은 검사를 쓴다.
  3. **값이 없는 실패도 고리에 넣는다.** 판정 없이 코드의 실패 이유로 행동을 고른다.
- 판정을 켜지 않아도 효과가 있는 보강 둘을 먼저 한다.
  - 사전 지름길 검사
  - 1위 표 recell

### 1-2. 판정 고리

```
판정 (Gemma, answer_judge.verdict)
  답 요약(지표 · 표 · 계산 · 지역 · 연도 · 성별 · 형태)을 보고 7가지 이유 중 하나
  ok → 그대로 / refuse → 기록만 / retry ↓
행동 고르기 (코드, agent_action.choose)
  판정 이유 × 처음 답의 경로(사전/표) × 1위 확실 여부 × 꾸러미 유무

  그 밖  → _recompute   ← 행동 이름을 보지 않고 처음 답의 경로만 봄
다시 판정 → ok면 교체, 아니면 새 이유로 다음 행동
한도: 다시 계산 2회 · LLM 행동 1회 · 60초 / 끝: _loop_end (되묻기 · 답변 불가 · 처음 답 + 주의)
```

### 1-3. 지금 행동과 실제 동작

| 행동 | 고르는 조건 | 실제 동작 |
|---|---|---|
| replan | 조건 · 계산 · 형태 · 기간 이유, 또는 코드 행동 뒤에도 틀림 | Gemma가 계획(대상 이유면 검색어까지)을 고침 → 새로 찾고 계산 |
| retable | 표 답 + 1위 불확실 | `_recompute`: 쓴 표를 빼고 다음 후보 |
| reroute | 사전 답 + 꾸러미 없음 | `_recompute`: 원래 질문으로 표 찾기 |
| requery | 사전 답 + 꾸러미 있음 | 호출부 없음 → `_recompute` (= 찾아 둔 꾸러미로 계산) |
| repick | 표 답 + 1위 확실 + 칸 실패 흔적 | 호출부 없음 → `_recompute` |
| give_up | 한도 · 답할 수 없음 | `_loop_end` |

- **"1위 확실"** (`top_is_sure`): 지표 하나 + 조건 확인이 비어 있지 않고 모두 ✔ + 표 검토 `exact`
- **조건 확인 ✔/✘** (`search.check`): 표 단위로 연도 범위 · 지역 단위 · 성별 구분 · 분류가 있는지 본다. ✘가 있는 표는 계산하지 않는다(`skip_reason`).

## 2. 문제 → 해결 → 설계

### 2-1. 행동 이름 겹침

- **문제:** `recell`이 둘이었다.
  - 표 계산 안에서 일상어 조건을 뜻으로 칸에 잇는 recell(#231, 실제로 돎)
  - 판정 고리의 행동 이름(호출부 없음)
  - trace에서 둘을 키 위치로만 구분할 수 있었다.
- **해결:** 판정 고리 쪽 이름을 바꿨다. #231 recell은 설정(`BINDING_RECELL`), trace 키, 평가 문서에 이미 쓰이고 있어 그대로 둔다.
- **설계:** 판정 고리 행동 `repick`("같은 표에서 칸 다시 고르기"). **완료** (`a44b84b`, 동작 변화 없음).

### 2-2. 행동이 고칠 단계가 아니라 사정으로 나뉨

- **문제:**
  - reroute와 requery는 "표 찾기를 이미 했느냐"로 갈린다. 둘 다 결국 "사전 표로는 안 되니 다른 표에서 찾는다"는 같은 일이다.
  - retable과 reroute도 "처음 답이 표냐 사전이냐"로 갈릴 뿐, 둘 다 "표 바꾸기"다.
  - requery의 근거("꾸러미에도 정답이 없다")는 확인된 적이 없다. 사전 답에 꾸러미가 있는 경우는 복합 게이트가 표를 **찾기만 하고 계산은 안 한** 경우뿐이다.
- **해결:** 행동을 **다시 하는 단계**로 나눈다. 후보를 새로 찾을지 있는 것을 쓸지는 행동 안에서 정한다.
- **설계:** 네 행동.

| 행동 | 다시 하는 단계 | 하는 일 | LLM |
|---|---|---|---|
| repick | 칸 | 같은 표(사전 표 포함)에서 칸 잇기 → recell. 판정의 지적과 틀린 칸을 함께 넘김 | recell 1회 |
| retable | 표 | 쓴 표(사전 표 · repick한 표 포함)를 빼고 다른 표로. 꾸러미가 있으면 남은 후보, 없으면 원래 질문으로 찾음. 검색어 그대로 | 없음 |
| replan | 계획 · 검색어 | Gemma가 계획을 고쳐 새로 찾고 계산 | Gemma 1회 |
| give_up | — | `_loop_end` 그대로 | — |

reroute는 retable에, requery는 replan에 합친다.

### 2-3. 행동 이름이 실제 동작을 가르지 못함

- **문제:** `_retry`는 replan이 아니면 행동 이름을 보지 않고 `_recompute`를 부른다. `_recompute`는 처음 답의 경로만 보고 다음 후보로 갈지, 표 찾기로 갈지를 정한다. 그래서 retable · reroute · requery · repick은 기록용 이름일 뿐이다.
- **해결:** 행동마다 실행 함수를 따로 둔다.
- **설계:** `_retry`가 `action.name`으로 나눈다.
  - `repick` → `_repick` (새로 만듦)
  - `retable` → `_retable`: 지금 `_recompute`의 두 갈래를 합치고, 사전 표와 repick한 표를 후보에서 뺀다.
  - `replan` → `_replan_compute` (그대로)

### 2-4. replan과 다른 행동이 겹침

- **문제:** replan은 계획을 고친 뒤 표 찾기와 계산을 전부 다시 한다. "대상이 다름"이면 검색어(`indicators[].search`)도 고친다([replan.py](../backend/app/agent/replan.py) `EDITABLE_DEFAULT`). 그래서 retable · requery와 범위가 겹친다.
- **해결:** 좁은 행동부터 쓰고, replan은 칸이나 표를 바꿔서는 안 될 때만 쓴다.
- **설계:** 행동 사다리 repick(칸) → retable(표) → replan(계획 · 검색어) → give_up. 같은 행동은 두 번 쓰지 않고, 같은 표를 두 번 계산하지 않는다.

### 2-5. 행동을 고르는 근거가 흩어져 있고 엉뚱함

- **문제:**
  - "1위 확실"은 조건 확인 ✔ + 검토 `exact`이다.
    - 조건을 말하지 않은 질문은 `checks`가 비어서 **늘 불확실**이 된다.
    - 검토 `partial`("조건이 조금 다름")도 늘 불확실이다. 그런데 이건 칸을 다시 고르면 고쳐질 수 있는 경우다.
  - repick은 `failed_at_cell`(계산 기록에 칸 실패 흔적이 있음)을 근거로 쓴다. 규칙이 막힘 없이 엉뚱한 칸("계")을 고르면 흔적이 없어서 놓친다.
  - 사전 게이트는 같은 일(질문 조건 → 칸 잇기 확인)을 사전 경로에서만 따로 한다.
- **해결:** "표가 맞나 · 칸으로 고칠 수 있나"를 **표의 칸을 직접 보고** 정한다. 사전 게이트의 칸 잇기 확인을 떼어 내서 한 곳에 둔다.
- **설계:** 검사 단계 (코드, LLM 없음. 조건 추출은 사전 게이트가 이미 하는 것을 다시 씀).

| | 내용 |
|---|---|
| 넣는 것 | 질문, 해석(parsed), 검사할 표 |
| 검사할 표 | 값을 낸 표 (사전 답이면 사전 지표의 출처 표). 값이 없으면 1위 후보 표. 아래 순위 표가 값을 냈으면 1위 표도 |
| `cells_ok` | 질문 조건이 모두 칸으로 이어짐 |
| `cells_exist` | 못 이은 조건에도 그 표에 맞는 분류 칸이 있음 → 칸을 다시 고르면 고칠 수 있음 |
| `kind_ok` | 묻는 값의 종류(수 · 비율 · 평균)와 지표 종류(`lookup.kind_of`)가 맞음 |
| `topic_ok` | 질문의 주제 말이 지표 이름 · 별칭 · 표 이름 · 칸 이름과 닿음 |
| `reasons` | 사람이 읽는 이유 목록 |

- **쓰는 곳:**
  - 사전 게이트: `cells_ok and kind_ok and topic_ok`일 때만 사전 답을 둔다.
  - 행동 고르기: `cells_exist`면 repick, 아니면 retable.
  - "1위 확실"과 `failed_at_cell`을 대신한다.

### 2-6. "조건이 빠짐"이 무조건 replan으로 감

- **문제:** 질문이 좁혀 물은 성별 · 나이 · 사유가 답에 없는 경우다. 이건 대부분 표는 맞고 칸("계")이 틀린 것이다. 그런데 지금은 가장 비싼 replan(Gemma + 새로 찾기)으로 간다.
- **해결:** 검사로 그 표에 칸이 있는지 보고, 있으면 칸만 다시 고른다.
- **설계:** 조건이 빠짐 + `cells_exist` → repick, 아니면 retable (규칙표 3-3).

### 2-7. 사전 답은 칸 다시 고르기가 없음

- **문제:** 사전 표에 질문의 분류 칸이 있어도, 사전 답이 틀리면 표 찾기나 replan으로만 간다. 사전 게이트가 "그대로"로 놓친 조건을 같은 표에서 고칠 길이 없다.
- **해결:** repick 대상에 사전 표를 넣는다.
- **설계:** `_repick`이 사전 표를 표 경로 계산으로 다시 돌린다. 칸은 고정하지 않고 칸 잇기 → recell을 쓴다. 사전 게이트는 1차(답 전) 확인으로 남고, repick은 게이트가 놓친 것을 고치는 2차 안전망이 된다.

### 2-8. 값이 없는 실패는 고리에 안 들어옴

- **문제:** 판정은 값이 나온 답만 받는다(`judgeable`). 표 계산이 모두 실패하면 행동 없이 통계표 안내나 답변 불가로 끝난다. 그런데 실패 이유는 코드가 이미 안다(`trace.dynamic`의 skip).
- **해결:** 값이 없는 실패는 Gemma 판정 없이 실패 이유로 행동을 고른다.
- **설계:** 고리 입구.

| 들어오는 것 | 근거 |
|---|---|
| 값이 나온 답 | Gemma 판정이 retry일 때: 판정 이유 + 검사 |
| 값이 없는 실패 (표 경로) | 판정 없이: 실패 이유 + 검사 (1위 후보 표) |
| 되묻기 · 답변 불가 사유 | 넣지 않음 (지금처럼 그대로 냄) |

### 2-9. recell이 "모든 후보 실패"일 때만 돎

- **문제:** 1위 표가 칸에서 막히고 2위 표가 값을 내면, 1위 표에는 recell을 시도하지 않는다(`run_round`). 근거:
  - 11/22 실험에서 재검색이 깨뜨린 19건 중 13건이 "표는 맞고 칸이 막힌 답"이었다.
  - 변형셋 평가의 "표는 맞는데 칸에서 막힘"은 4건 → 6건이었다.
- **해결:** 판정 없이도, 값이 나온 표보다 순위가 높은 표에 recell을 1회 시도한다. 칸 LLM은 이미 같은 자리에서 이렇게 하고 있다([dynamic_indicator.py](../backend/app/services/dynamic_indicator.py) `run_round`).
- **설계:** 두 표가 다 값을 내면 아래 순서로 고른다.
  1. 조건 확인이 모두 ✔
  2. 칸을 이은 방식: 규칙 · 칸 잇기로 다 이음 > recell 뜻으로 이음 > 더 넓은 칸으로 대신함
  3. 순위

  순위만 따르면, 1위의 "뜻으로 이은" 답이 2위의 정확한 답을 밀어낼 수 있다. 그래서 **이 기준은 devset · 변형셋으로 "1위 recell 답 vs 2위 답"을 재 본 뒤 넣는다.**

### 2-10. 사전 지름길이 지표 해석을 확인하지 않음

- **문제:** 지표 이름이 질문에 글자로 없는 사전 답(`ungrounded_by="name"`)은 사전 게이트가 조건만 보고 사전 답을 둔다.
  - 원래 "주제 말이 어느 칸과도 맞지 않으면 넘김" 확인(`binding._bind_topic`)이 있다.
  - 그런데 사전 표는 항목 칸(`item_id`)을 고정해 두기 때문에, 이 확인이 **늘 통과**한다.
  - 그래서 HCX가 일상어를 틀린 지표로 읽어도 그대로 나간다. 변형셋 P-103: 비율을 물었는데 건수 지표로 답했다.
- **해결:** 지름길일 때는 지표 해석도 확인한다.
- **설계:** 검사의 `kind_ok` · `topic_ok`를 사전 게이트에 쓴다.
  - 비율 말(`비율`, `~당`, `몇 명꼴`, `%`, `~률`)이 있는데 지표가 건수면 넘긴다. 반대도 같다.
  - 주제 말이 지표 이름 · 별칭 · 표 이름 · 고정 칸 이름과 하나도 닿지 않으면 넘긴다.
  - 지름길로 맞게 고친 P-038 · P-059는 지켜야 한다.

### 2-11. 판정 고리가 기본 꺼짐, 판정 오류

- **문제:**
  - `ANSWER_JUDGE`가 꺼져 있어서 기본 설정에서는 고리의 행동이 하나도 돌지 않는다.
  - 판정은 맞는 답 107 중 12를 막았다. 형태를 요약에 적지 않았을 때는 30을 막았다.
- **해결:** 켤지는 측정으로 정한다.
- **설계:** 4장 작업 순서 6단계. devset · 변형셋에서 켬/끔을 비교하고 고친 수와 깨진 수를 함께 센다.

### 2-12. 복합 게이트 비용

- **문제:** 새 질문마다 Gemma 1회가 붙는다. 사전으로 끝나는 질문도 LLM을 세 번 부른다(질문 이해 · 사전 게이트 조건 추출 · 복합 판별). 측정이 없다.
- **해결 · 설계:** trace `llm_calls`로 질문당 호출 수와 시간을 집계한다. 사전으로 끝나는 질문에서 앞단 규칙으로 건너뛸 수 있는지 본다. 이 문서의 범위 밖이고 측정만 한다.

## 3. 변경 후 설계

### 3-1. 흐름

```
질문 → ① 거절 거르기 → ② 질문 이해 → ③ 사전 계산
 ④ 사전 게이트 = [검사] 사전 표: cells_ok · kind_ok · topic_ok      ← 2-5 · 2-10
      모두 참 → 사전 답 / 아니면 → ⑥
 ⑤ 복합 게이트 (그대로)
 ⑥ 표 경로: 표 찾기 → 후보 계산
      1위 칸 막힘 + 아래 표가 값 냄 → 1위에 recell 1회 (비교 기준 2-9)  ← 2-9
 ⑦ 판정 고리
      [고리 입구] 값 있음: Gemma 판정 retry / 값 없음: 판정 없이 실패 이유   ← 2-8
      [검사] 값을 낸 표 (값이 없으면 1위 후보 표, 아래 순위 표가 답했으면 1위 표도)
      [행동 고르기] repick → retable → replan → give_up                   ← 2-2 · 2-4
      [실행] 행동별 함수                                                  ← 2-3
      다시 한 답 → 고리 입구로 (값 있으면 다시 판정, ok면 교체)
```

### 3-2. 네 행동

2-2의 표와 같다. 한도는 지금처럼 둔다: 다시 계산 2회, LLM 행동(repick의 recell · replan) 합쳐 1회, 60초.

### 3-3. 행동 고르기 규칙

| 판정 이유 · 실패 | 검사 | 행동 | 안 되면 |
|---|---|---|---|
| 조건이 빠짐 | 칸 있음 | repick | retable |
| 조건이 빠짐 | 칸 없음 | retable | replan |
| 대상이 다름 | 칸 있음 · 값 종류 · 주제 맞음 | repick | retable |
| 대상이 다름 | 그 밖 | retable | replan |
| 계산이 빠짐 · 형태가 다름 · 기간이 다름 | — | replan | retable |
| 값 없음: 칸 일부만 이어짐 | 칸 있음 | repick | retable |
| 값 없음: 후보 모두 조건 ✘ | — | replan | give_up |
| retable 뒤에도 대상이 다름 | — | replan | give_up |
| 답할 수 없는 질문 · 한도 초과 | — | give_up | — |

### 3-4. 지금과 비교

| | 지금 | 변경 후 |
|---|---|---|
| 행동 | 6개 | 4개 (reroute → retable, requery → replan) |
| 행동이 동작을 가르나 | replan 말고는 모두 `_recompute` | 행동마다 함수 |
| 근거 | 판정 이유 × 처음 답의 경로 × 1위 확실 × 꾸러미 유무 | 판정 · 실패 이유 × 검사 |
| 값 없는 실패 | 고리 밖 | 고리 안 (판정 없이) |
| 사전 답 칸 다시 고르기 | 없음 | repick |
| 사전 지름길 | 조건만 확인 | 조건 + 값 종류 + 주제 |
| 1위 표 recell | 모든 후보 실패 때만 | 아래 순위 표가 답해도 1회 |

## 부록. 용어

| 말 | 뜻 |
|---|---|
| 사전 게이트 (옛 이름 사전 문지기) | 사전 답이 질문 조건을 다 담았는지 코드로 확인해 그대로 / 넘김을 정하는 단계 (`dict_binding`) |
| 복합 게이트 | 여러 단계 계산이 필요한 질문인지 Gemma가 판단하는 단계 (`composite`) |
| 사전 지름길 | 지표 이름이 질문에 없어도 사전 게이트를 통과하면 사전 답을 두는 규칙 (D1) |
| 꾸러미 | 표 찾기 결과 묶음: 계획 + 후보 표(✔/✘, 검토, 1위) (`found["handoff"]`) |
| 칸 잇기 | 질문 조건을 표의 분류 칸(코드)에 연결 (`binding`) |
| recell | 칸 잇기가 못 이은 일상어 조건을 LLM이 뜻으로 칸에 이음 (#231) |
| 판정 | 답이 질문에 맞는지 Gemma가 보는 것. ok / retry / refuse |
| 검사 | (새) 표에 질문 조건이 칸으로 이어지는지, 값 종류 · 주제가 맞는지 코드가 보는 것 |

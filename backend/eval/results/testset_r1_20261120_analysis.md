### 채점 정정 (정답 표기 10문항)

처음 채점(A 42.6% · B 37.0%)은 정답 수치 칸 표기 탓에 낮게 나왔다. 채점기(`scripts/devset_grade.expected_numbers`)는 질문 종류마다 정해진 표기에서 맞아야 하는 숫자를 뽑는데
(집계 "합계 N", 순위 "1위 이름 N", 비교 "차이 N · N배", 추이 "증감량 · 증감률 · 연평균" 또는 "증감 N%p"),
테스트셋 10문항(집계 6 · 추이 2 · 비교 1 · 순위 1)이 이 표기를 따르지 않아 **맞는 답도 무조건 틀림**이 됐다.
숫자는 그대로 두고 표기만 고쳐(v1.1) 저장해 둔 원응답을 다시 채점했다(`--regrade`, 챗봇은 다시 부르지 않음). 개발셋 v2에는 같은 문제가 없다(0문항).

## 3. 표는 찾았는데 계산 못 한 8건 (경로 ③)

통계표 찾기는 맞는 표를 골랐고, 표에서 바로 계산하는 단계(`dynamic_indicator`)에서 멈춰 "이 통계표에서 확인하세요"로 끝난 문항이다. 채점기의 '표 찾고도 거절한 원인' 분류.

## 5. 답변 불가 14문항

| 기대 유형 | A 실제 | B 실제 |
|---|---|---|
| 없는 연도 (out_of_range) | 맞음 | 맞음 |
| 값이 비어 있음 (missing_data) ×2 | 맞음 | 맞음 |
| 맞는 구간 없음 (band_mismatch) | 맞음 | 맞음 |
| 범위 밖 주제 (out_of_scope) ×2 | 맞음 | 맞음 |
| 원인 질문 (causal_question) | 맞음 | 맞음 |
| 그해에 없던 지역 (region_not_in_year) | out_of_range (유형 틀림) | out_of_range (유형 틀림) |
| 없는 지역 단위 (no_region_level) | out_of_scope (유형 틀림) | 통계표 안내 (유형 틀림) |
| 조건을 모두 만족하는 표 없음 (partial_match) | out_of_scope (유형 틀림) | **답함** |
| 함께 집계한 통계 없음 (no_joint_table) | **답함** | **답함** |
| 예측 질문 (prediction_question) | **답함** | **답함** |
| 통계 질문이 아님 (not_statistics) | out_of_scope (유형 틀림) | out_of_scope (유형 틀림) |
| 통계 질문이 아님 (chat) | out_of_scope (유형 틀림) | out_of_scope (유형 틀림) |

- 거절은 하는데 **유형을 out_of_scope 하나로 뭉뚱그리는 것**이 5건(A)이다. 통계표 찾기의 후보 검토가 "맞는 표 없음"으로 끝나면 이유와 관계없이 범위 밖으로 안내한다.
  나눠야 할 것: 인사 · 행정 절차(통계 질문 아님), 시군구 자료가 없는 지표(없는 지역 단위), 세부 구분이 없는 표(조건 만족 표 없음).
- **거절해야 하는데 답한 것** 2건(A): 두 대상을 함께 센 통계가 없는데 한쪽만 세어 답함, 예측 질문을 장래인구추계 값으로 답함.
  뒤의 것은 골든셋이 '답변 불가 + 장래추계 안내'를 기대한 문항이라, 장래추계 값을 답으로 줄 때 어떻게 채점할지 **채점 기준 확인 필요**.
- 그해에 없던 지역을 '없는 연도'(자료 연도 범위)로 안내했다. 지역 출범 연도로 안내해야 한다.

## 6. Gemma와 HCX 비교 (A vs B)

- 68문항 중 **64문항은 결과가 같고**, 다른 4문항은 **모두 Gemma에서만 맞았다** (HCX에서 맞고 Gemma에서 틀린 문항 0).
  HCX에서 틀린 이유: 표 안내 · 거절로 끝남 3, 필요 없는 되묻기 1.
- 경로 ②(표에서 바로 계산)의 정답이 2/10 → 5/9로 가장 크게 달라졌다. 표 찾기 · 칸 고르기에서 Gemma가 낫다.
- LLM 호출은 Gemma 쪽이 문항당 0.6회 적다. HCX는 칸 고르기를 23회(13문항) 불렀고 Gemma 실행은 6회였다 (Gemma 실행에서는 규칙으로 정해진 칸이 많음).
- 응답 시간: 적재 경로는 A가 3초 느리지만, 공통 단계인 질문 이해(HCX)의 평균이 A 4.8초 · B 3.2초로 달라 **HCX 응답 속도 차이가 섞여 있다**. Gemma 자체가 느리다고 보기 어렵다. API 경로는 A가 7초 빠르다.
- 한 번씩만 돌린 결과라 차이 4문항(7%p)은 LLM 응답의 흔들림 범위일 수 있다. 같은 조건으로 한 번 더 돌려 보면 확실해진다.

## 7. 다음에 볼 곳 (건수 순, 개발셋에서 같은 유형으로 확인)

1. **표 칸 고르기** (경로 ③ 5건 + 경로 ② 표 3건): 일상어 ↔ 칸 이름 연결, 여러 칸 합산 질문. `dynamic_indicator.choose` · `uncovered` · `cell_pick`
2. **답변 불가 유형 나누기** (5건): 후보 검토가 "맞는 표 없음"일 때 통계 질문 아님 · 없는 지역 단위 · 조건 만족 표 없음을 구분. `search.check` · 답변 불가 안내
3. **사전 지표의 기본 표와 질문 대상이 다를 때** (경로 ① 표 4건): 질문이 사전 지표보다 좁은 대상을 물으면 표 찾기로 넘길지. `qa` 지표 매칭
4. **API 문항의 표 고르기** (④ 3건): 오래된 표(적재 안 됨)를 후보 검토가 "질문 주제 아님"으로 거절. 후보 검토 프롬프트에서 연도 범위 · 조사 기준(예: 90일 넘게 머문 출국자)을 다루는지
5. **세부 구분이 있는 표로 넘기기 · 칸 후보 2개일 때 되묻기** (⑤ 2건 · ⑥ 3건)

## 재현

```
cd backend
python -m scripts.eval_devset --golden <테스트셋 CSV> --round 1 --version v1.1 --note "…"
python -m scripts.eval_devset --golden <테스트셋 CSV> --regrade data/eval/devset_r1_….raw.jsonl   # 채점만 다시
```

- 테스트셋 CSV와 문항별 결과(`backend/data/eval/devset_r1_20261120_*`)는 깃에 올리지 않는다.
- API 문항은 첫 실행에서만 API 경로다 (실행 중 받은 표가 적재됨). 두 실행 모두 끝난 뒤 실행 중 적재된 표(27개 · 12개)를 지워 실행 전 상태(표 804개)로 되돌렸다.
- Gemma 주소가 셸 환경변수에 예전 값으로 남아 있으면 `.env`보다 먼저 쓰여 연결이 실패한다 (실행 B가 그 경우). 실행 A는 `env -u GEMMA_BASE_URL -u GEMMA_API_KEY -u GEMMA_MODEL`로 `.env` 값을 썼다.
